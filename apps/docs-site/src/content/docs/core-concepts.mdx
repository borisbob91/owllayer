**DomOS est un SDK d'AI-driven interfaces, ou interfaces agentiques.** Il ne remplace pas votre interface et ne génère pas une nouvelle UI par-dessus votre produit. Il permet à un agent IA d'agir dans l'interface existante avec des actions explicites, un contexte observable et des garde-fous.

## Agentic UI

Une interface agentique est une interface que l'agent peut piloter par des points d'entrée explicites.

L'agent ne manipule pas librement le DOM. Il ne devine pas les clics à effectuer. Il reçoit un contexte structuré et une liste de tools déclarés par l'application, puis il agit uniquement à travers ces tools.

Cela distingue DomOS de deux approches proches :

- un chatbot classique, qui repond surtout par du texte ;
- une Generative UI, qui fabrique une nouvelle interface au lieu de piloter l'interface existante.

Dans DomOS, l'application reste propriétaire de sa logique métier. L'agent appelle seulement les actions que le produit accepte d'exposer.

## Neural-DOM Binding

Le **Neural-DOM Binding** est le concept architectural central de DomOS. Il designe la liaison controlee entre une interface deja existante, le contexte que cette interface accepte de partager, et le raisonnement d'un agent IA.

Le modele ne recoit pas un acces libre au DOM. Il recoit un contrat : un **Shadow Context** structure, une liste de tools actifs, et un protocole d'echange. Quand il veut agir, il ne clique pas directement dans l'interface ; il demande l'execution d'un tool declare par l'application.

Le principe se lit en trois couches :

| Couche | Role | Regle DomOS |
| --- | --- | --- |
| DOM visible | Ce que l'utilisateur voit et manipule reellement | L'agent ne le parcourt pas librement |
| Shadow Context | Representation utile de l'ecran, des donnees visibles et des tools montes | Seul ce contexte est synchronise avec le serveur |
| Session agentique | Runtime serveur, adapter LLM et decisions de tool calls | Le LLM ne voit que les tools presents dans la session courante |

Le mot **Binding** est important : le lien n'est pas statique. Quand une page, une carte produit, une modale ou un formulaire apparait, ses tools peuvent entrer dans le Shadow Context. Quand cette UI disparait, ses tools doivent etre retires et le serveur doit recevoir un nouveau `CONTEXT_UPDATE`. C'est ce qui evite les actions hors contexte.

Le mot **Neural** designe la partie decisionnelle : le modele raisonne sur le contexte autorise, puis choisit eventuellement un tool. Mais l'execution reste dans le code applicatif, avec les schemas, permissions, validations HITL et handlers definis par le produit.

## Le runtime commun : DomOSClient

`DomOSClient` est le coeur front de DomOS. Les SDK frameworks ajoutent une ergonomie adaptee a leur environnement, mais ils partagent le meme runtime.

| SDK | Integration principale | Runtime |
| --- | --- | --- |
| React | `DomOSProvider`, hooks, composants | `DomOSClient` |
| Vue | plugin, composables, composants | `DomOSClient` |
| Svelte | stores, actions, composants | `DomOSClient` |
| Angular | provider, injection, signals, directives | `DomOSClient` |
| Browser | API JavaScript directe, auto-discovery HTML | `DomOSClient` |

Ce que le client partage entre tous les frameworks :

- connexion WebSocket ADTP ;
- registre local des tools ;
- synchronisation du contexte ;
- execution des tool calls ;
- emission des tool results ;
- etat de session et evenements runtime.

React, Vue, Svelte, Angular et Browser changent la facon de declarer les tools. Ils ne changent pas le protocole.

## ADTP

ADTP signifie **Agent-to-DOM Transfer Protocol**.

C'est le protocole JSON sur WebSocket qui relie le client DomOS au serveur DomOS.

| Message | Direction | Role |
| --- | --- | --- |
| `HANDSHAKE_INIT` | Client vers serveur | Annonce les versions SDK et protocole à l'ouverture du socket |
| `HANDSHAKE_ACK` | Serveur vers client | Confirme la session créée après authentification |
| `CONTEXT_UPDATE` | Client vers serveur | Synchronise URL, contexte et tools actifs |
| `USER_INPUT` | Client vers serveur | Envoie un message texte ou audio utilisateur |
| `TOOL_CALL` | Serveur vers client | Demande l'execution d'un tool client |
| `TOOL_RESULT` | Client vers serveur | Retourne le resultat du tool |
| `AGENT_RESPONSE` | Serveur vers client | Transmet la reponse de l'agent |
| `SYSTEM_EVENT` | Bidirectionnel | Signale erreurs, notifications ou controle runtime |

Le serveur ne peut appeler que les tools connus dans le contexte de session courant.

## Shadow Context

Le Shadow Context est la representation legere de l'etat utile de l'interface.

Il ne copie pas tout le DOM. Il contient uniquement les informations que l'application choisit d'exposer :

- URL et titre courant ;
- page ou vue active ;
- entite visible ;
- selection courante ;
- filtres actifs ;
- panier, dossier, etape de workflow ou autres donnees metier utiles ;
- liste des tools actifs.

Le contexte passif aide le modele a comprendre la situation. Il ne cree pas d'action. Les actions restent portees par les tools.

## Tools

Un tool est une action metier que l'agent est autorise a declencher.

Un bon tool a :

- un nom stable ;
- une description metier claire ;
- un schema d'arguments precis ;
- un niveau de risque HITL coherent ;
- un handler qui realise l'action et retourne un resultat utile.

Les tools client sont dynamiques. Ils vivent au rythme de l'interface :

| Cycle UI | Effet DomOS |
| --- | --- |
| Composant monte | Le tool peut etre enregistre |
| Composant detruit | Le tool doit etre retire |
| Navigation | La liste des tools change |
| Contexte modifie | Le serveur recoit un nouveau `CONTEXT_UPDATE` |

Ce modele evite de donner au LLM une liste globale d'actions hors contexte. L'agent voit les actions pertinentes pour l'ecran courant.

## Cycle de vie d'un composant agentique

Dans DomOS, un tool client n'est pas seulement une fonction disponible quelque part dans l'application. Il est lie au cycle de vie de l'interface qui le declare.

Ce cycle est la mise en pratique du **Neural-DOM Binding** : le composant UI devient le point d'attache entre le DOM visible, le handler JavaScript local et le contexte que le serveur donne au LLM. Le **Shadow Context** est la partie synchronisee de ce binding : il contient l'etat utile de l'ecran et la liste des tools actuellement montes.

:::note[Shadow Context, pas Shadow DOM]
Le Shadow Context est le contexte logique envoye au serveur. Il ne faut pas le confondre avec le Shadow DOM utilise par certains composants UI pour isoler leurs styles ou les controles HITL.
:::

Un composant agentique traverse deux cycles complementaires :

- le cycle actif, quand le composant est monte et que son tool peut etre vu par l'agent ;
- le cycle de cleanup, quand le composant disparait et que le tool doit etre retire du contexte de session cote serveur.

  <img
    src={componentToolLifecycle.src}
    alt="Cycle de vie d'un composant DomOS : montage, enregistrement du tool, CONTEXT_UPDATE, decision LLM, TOOL_CALL, TOOL_RESULT, puis unmount et synchronisation de suppression."
  />
</div>

Le cycle actif est le flux normal :

1. Le composant est monte dans l'interface.
2. Le SDK framework enregistre sa declaration de tool et son handler dans le `ToolRegistry` local de `DomOSClient`.
3. `DomOSClient` envoie un `CONTEXT_UPDATE` avec les tools actifs et le contexte courant.
4. `DomOSServer` met a jour la session. Au prochain message utilisateur, le serveur donne au LLM uniquement les tools visibles dans cette session.
5. Si le LLM choisit ce tool, le serveur envoie un `TOOL_CALL` au client.
6. `DomOSClient` execute le handler local du composant, attend son resultat, puis renvoie `TOOL_RESULT`.

Le cycle de cleanup est aussi important que le montage :

1. Le composant est demonte ou la route change.
2. Le SDK retire le tool du registre local, par nom ou par `componentId`.
3. `DomOSClient` envoie un nouveau `CONTEXT_UPDATE`.
4. La session serveur desynchronise ce tool et ne le presente plus au LLM.

Cette mecanique evite les tools fantomes : une action liee a une carte produit, un formulaire, une modale ou une vue detail ne reste pas disponible quand cette UI n'existe plus.

### Mapping par SDK

| SDK | Declaration | Enregistrement | Cleanup |
| --- | --- | --- | --- |
| React | `useAgentTool()` | `useEffect()` enregistre le tool quand le composant est monte | cleanup du hook, sauf `global: true` |
| Vue | `useAgentTool()` | `onMounted()` enregistre le tool | `onUnmounted()` retire le tool, sauf global |
| Svelte | `use:agentTool` | l'action Svelte enregistre le tool sur le noeud | `destroy()` retire le tool |
| Angular | service, directive ou resolver | le service enregistre le tool dans `DomOSClient` | `OnDestroy` / cleanup explicite selon l'integration |
| Browser | `DomOS.registerTool()` ou auto-discovery | le runtime enregistre le tool comme global ou DOM-discovered | `unregisterTool()` ou retrait DOM detecte |

### Exemple React

React illustre bien le principe : `useAgentTool()` suit le cycle de vie du composant. Quand `ProductCard` est rendu, le tool `add_visible_product_to_cart` est synchronise avec le serveur. Quand la carte sort du DOM, le hook nettoie le registre local et le serveur recoit un `CONTEXT_UPDATE` sans ce tool.

```tsx
import { useAgentTool } from '@domos/react';
import { z } from 'zod';

type Product = {
  id: string;
  name: string;
};

export function ProductCard({ product }: { product: Product }) {
  useAgentTool(
    {
      name: 'add_visible_product_to_cart',
      description: `Ajouter le produit visible "${product.name}" au panier.`,
      schema: z.object({
        quantity: z.number().min(1).default(1),
      }),
      risk: 'low',
    },
    async ({ quantity }) => {
      await cartApi.add(product.id, quantity);
      return {
        added: true,
        productId: product.id,
        quantity,
      };
    }
  );

  return <article>{product.name}</article>;
}
```

Dans cet exemple, le LLM ne voit pas un tool global abstrait du type "ajoute n'importe quel produit". Il voit l'action contextualisee par l'interface courante : cette carte produit precise, avec son `product.id` capture par le handler React. Si la carte est demontee, cette action disparait aussi du Shadow Context cote serveur.

### Tools locaux et tools globaux

Tous les tools ne doivent pas suivre un composant precis.

Un tool local doit disparaitre avec son composant. Exemples : `select_product_card`, `edit_current_row`, `open_visible_modal`.

Un tool global peut survivre a la navigation. Exemples : `navigate`, `open_cart`, `set_theme`, `logout`. Dans ce cas, l'integration doit le declarer explicitement comme global ou le placer dans un resolver central.

La regle pratique est simple : **si l'utilisateur ne voit plus l'objet ou l'ecran concerne, le LLM ne doit plus voir le tool correspondant.**

## Contrat d'execution d'un tool

Quand le serveur envoie un `TOOL_CALL`, `DomOSClient` cherche le tool local correspondant, execute son handler, puis renvoie un `TOOL_RESULT`.

Le contrat important est simple : **DomOS attend uniquement la Promise retournee par le handler du tool.**

Tout travail asynchrone necessaire au resultat doit donc etre retourne ou `await` dans ce handler.

### Correct

```ts
domos.registerTool(
  { name: 'archive_ticket', description: 'Archiver le ticket courant' },
  async ({ ticketId }) => {
    const result = await api.archiveTicket(ticketId);
    return { archived: true, id: result.id };
  }
);
```

### Incorrect

```ts
domos.registerTool(
  { name: 'archive_ticket', description: 'Archiver le ticket courant' },
  ({ ticketId }) => {
    api.archiveTicket(ticketId);
    return { archived: true };
  }
);
```

Dans le second exemple, l'appel API est detache. DomOS peut envoyer `TOOL_RESULT` avant la fin reelle de l'action. Si l'appel API echoue ensuite, cette erreur sort du contrat d'execution du tool.

Eviter en particulier :

- Promises lancees sans `return` ni `await` ;
- `subscribe()` RxJS non converti en Promise quand le resultat compte pour le tool ;
- `setTimeout()` utilise comme effet secondaire non attendu ;
- mutations d'etat declenchees apres le retour du handler alors qu'elles font partie du resultat attendu.

## Angular et code asynchrone

Le contrat est identique dans tous les SDK. Dans le code actuel, `DomOSClient` appelle le handler enregistré avec `await tool.handler(...)`, puis envoie `TOOL_RESULT` en succès ou en erreur. La bonne règle d'intégration ne dépend donc pas d'une différence supposée entre frameworks : **le handler doit représenter toute l'opération attendue par l'agent**.

Dans une application Angular, cette règle est particulièrement importante lorsque le code métier s'appuie sur RxJS ou sur des effets déclenchés par un composant. Un `subscribe()` détaché ou un effet lancé sans retour peut terminer après le handler : DomOS a alors déjà reçu un résultat incomplet ou trop précoce.

Avec RxJS, preferer une Promise explicite quand le tool depend du resultat :

```ts
import { firstValueFrom } from 'rxjs';

domos.registerTool(
  { name: 'load_order', description: 'Charger la commande courante' },
  async ({ orderId }) => {
    const order = await firstValueFrom(orderService.load(orderId));
    return { orderId: order.id, status: order.status };
  }
);
```

Le point à retenir : React, Vue, Svelte, Angular et Browser utilisent le même contrat d'exécution DomOS. Retournez une Promise qui ne se résout qu'une fois le résultat du tool réellement disponible.

## HITL

HITL signifie **Human-in-the-Loop**.

DomOS classe les tools par niveau de risque :

| Risque | Comportement attendu | Exemple |
| --- | --- | --- |
| `none` | Execution directe | `search_products` |
| `low` | Execution directe avec notification possible | `add_to_cart` |
| `high` | Confirmation utilisateur requise | `clear_cart` |
| `critical` | Confirmation utilisateur renforcee requise | `process_payment` |

Le risque doit refleter l'impact utilisateur reel, pas la complexite technique du handler.

## Widget

Le widget DomOS fournit une interface conversationnelle texte ou voix.

Il n'est pas le coeur de DomOS. Le coeur reste le triptyque :

- contexte ;
- tools ;
- protocole ADTP.

Le widget est une surface utilisateur prete a l'emploi pour interagir avec l'agent. Une application peut utiliser le widget officiel ou construire sa propre UI autour du meme `DomOSClient`.

## Anti-patterns

Ces pratiques affaiblissent le modele DomOS :

- declarer tous les tools globalement au demarrage ;
- donner au LLM des tools hors contexte ;
- utiliser des noms de tools ambigus ;
- mettre de la logique metier critique dans une description au lieu du handler ;
- retourner un succes avant que l'action asynchrone soit terminee ;
- confondre contexte passif et action ;
- exposer une action risquee avec `risk: 'none'` ;
- creer un tool par item dans une longue liste au lieu d'un tool bien parametre.

DomOS fonctionne bien quand l'application expose peu d'actions, mais des actions justes, contextualisees et verifiables.
