Cette page configure le chemin le plus court : une session texte sur WebSocket avec un adapter LLM. L'application frontend se connectera ensuite à l'endpoint AITP exposé par ce serveur.

## Prérequis

- Node.js et `pnpm` installés ;
- une clé fournisseur pour Google Gemini ou OpenAI ;
- une clé client OwlLayer que votre frontend utilisera pour ouvrir la connexion.

## Installer les packages

Avec Gemini :

```bash
pnpm add @owllayer/server @owllayer/adapter-google dotenv
```

Avec OpenAI :

```bash
pnpm add @owllayer/server @owllayer/adapter-openai dotenv
```

## Créer le serveur

Exemple Gemini :

```ts
// server.ts
import 'dotenv/config';
import { OwlLayerServer } from '@owllayer/server';
import { GoogleAdapter } from '@owllayer/adapter-google';

const googleApiKey = process.env.GOOGLE_API_KEY;
const clientApiKey = process.env.OWLLAYER_CLIENT_API_KEY;

if (!googleApiKey || !clientApiKey) {
  throw new Error('GOOGLE_API_KEY et OWLLAYER_CLIENT_API_KEY sont requis');
}

const server = new OwlLayerServer({
  llm: new GoogleAdapter({
    apiKey: googleApiKey,
    model: 'gemini-2.5-flash',
    systemPrompt: 'Tu aides l utilisateur a agir dans l interface courante.',
  }),
  port: 3000,
  path: '/owllayer',
});

server.addApiKey(clientApiKey);

server.listen(() => {
  console.log('OwlLayer disponible sur ws://localhost:3000/owllayer');
});
```

```bash
GOOGLE_API_KEY=your_google_key
OWLLAYER_CLIENT_API_KEY=pk_dev_local
```

Lancer le fichier avec votre exécuteur TypeScript habituel, par exemple `tsx server.ts`.

## Relier le frontend

Le client SDK ouvre le WebSocket et présente sa clé client :

```ts
const client = new OwlLayerClient({
  endpoint: 'ws://localhost:3000/owllayer',
  apiKey: 'pk_dev_local',
});

client.connect();
```

Dans le runtime actuel, le serveur vérifie la clé dès l'ouverture de la connexion WebSocket, associe la connexion à une session et émet `HANDSHAKE_ACK`. En parallèle, `OwlLayerClient` émet `HANDSHAKE_INIT` à l'ouverture de son socket ; ce message permet notamment de vérifier la version AITP. Votre application ne doit pas dépendre d'un ordre supplémentaire entre ces deux messages d'initialisation.

## Options essentielles

| Option | Rôle | Défaut observé |
| --- | --- | --- |
| `llm` | Adapter texte requis pour traiter une demande utilisateur. | Requis |
| `port` | Port HTTP/WS créé par OwlLayer si aucun serveur HTTP n'est fourni. | `3000` |
| `path` | Chemin WebSocket AITP. | `/owllayer` |
| `server` | Serveur HTTP Node existant à réutiliser. | Aucun |
| `allowedOrigins` | Origines Web autorisées lors de la connexion. | Toutes si absent |
| `toolTimeout` | Durée maximale d'attente d'un tool client routé. | `10 000 ms` dans `ToolRouter` |
| `maxConversationMessages` | Taille de la fenêtre conversationnelle conservée. | `50` dans `SessionManager` |

## Ajouter l'audio plus tard

Le serveur reste texte uniquement tant que vous ne fournissez pas d'adapter ou de services audio :

```ts
const server = new OwlLayerServer({
  llm,
  live, // GoogleLiveAdapter ou OpenAILiveAdapter
  port: 3000,
});
```

Ou, pour un pipeline découplé :

```ts
const server = new OwlLayerServer({
  llm,
  stt,
  tts,
  port: 3000,
});
```

Le premier mode échange directement des flux audio avec un modèle live. Le second suit la chaîne `audio -> STT -> LLM texte -> TTS -> audio`.

## À propos des tools backend

`server.tool(name, handler)` enregistre un handler disponible pour le routeur serveur. Dans le code actuel, les déclarations envoyées au LLM proviennent du registre de tools de la session, alimenté par le frontend via `CONTEXT_UPDATE`. Un handler serveur enregistré seul ne constitue donc pas, à lui seul, une capacité automatiquement annoncée au modèle.

Cette distinction est importante pour publier une intégration fiable : documentez comme outils agent visibles ceux que le runtime transmet effectivement au modèle.
