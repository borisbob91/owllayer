Un serveur OwlLayer reçoit des demandes susceptibles de modifier une interface ou d'atteindre un backend. La configuration de production commence donc par quatre questions : qui se connecte, quelle origine est admise, quelle action nécessite une validation et quelles données doivent survivre au processus Node.js.

## Authentification des clients

Par défaut, `ClientAuthManager` exige une API key. Le client peut la présenter dans la requête WebSocket :

- par query string : `?apiKey=...` ;
- par en-tête `Authorization: Bearer ...`.

Pour un développement local :

```ts
const server = new OwlLayerServer({ llm, port: 3000 });
server.addApiKey(process.env.OWLLAYER_CLIENT_API_KEY!);
```

Pour une stratégie externe, le serveur accepte un validateur :

```ts
server.setApiKeyValidator(async (key) => {
  return await keyService.isAllowed(key);
});
```

`client.maxConnectionsPerKey` limite les connexions simultanées d'une même clé ; la valeur par défaut du gestionnaire est `10`.

## Origines et capacité

Deux options évitent d'ouvrir un endpoint trop largement :

```ts
const server = new OwlLayerServer({
  llm,
  port: 3000,
  allowedOrigins: ['https://app.example.com'],
  maxConnections: 500,
});
```

`allowedOrigins` est vérifié à la connexion. Sans liste fournie, le serveur n'applique pas de restriction d'origine. `maxConnections` est appliqué par le transport WebSocket global.

Une API key navigateur est visible dans le code du site. En production, réservez chaque clé à ses origines :

```ts
server.addApiKey('pk_shop', { allowedOrigins: ['https://shop.example.com'] });
```

Une connexion avec cette clé depuis une autre origine, ou sans en-tête `Origin` (script), est refusée. La même information peut être fournie à la création d'une clé par l'API admin (`POST /admin/client/keys`, champ `allowedOrigins`).

## Limites de taille et de débit

Les limites protègent la mémoire du serveur et le budget LLM. Elles s'appliquent par défaut :

| Option | Défaut | Au-delà |
| --- | --- | --- |
| `limits.maxMessageBytes` | 4 Mo | la connexion WebSocket est fermée (code 1009) |
| `limits.maxTextInputChars` | 8 000 caractères | le message est refusé, sans appel au LLM |
| `limits.maxClientTools` | `maxActiveTools` (30) | le `CONTEXT_UPDATE` est refusé ; une valeur inférieure à `maxActiveTools` empêche le serveur de démarrer |
| `limits.maxContextBytes` | 64 Ko | le `CONTEXT_UPDATE` est refusé |
| `rateLimit.messagesPerSecond` | 100 par connexion | le message est refusé |
| `rateLimit.userInputsPerMinute` | 20 par connexion | le message utilisateur est refusé |
| `rateLimit.userInputsPerMinutePerKey` | désactivé | plafond commun à toutes les connexions d'une clé |

Les corps des requêtes HTTP (API admin, lignes virtuelles, signalisation WebRTC) sont limités à 64 Ko (réponse `413`).

```ts
const server = new OwlLayerServer({
  llm,
  limits: { maxMessageBytes: 8 * 1024 * 1024 },
  rateLimit: { userInputsPerMinutePerKey: 600 },
});
```

`userInputsPerMinutePerKey` est le vrai plafond de coût : réglez-le selon le trafic attendu de chaque application.

Une session traite aussi **un seul tour LLM à la fois**. Un message utilisateur reçu pendant que l'assistant répond, y compris pendant qu'une approbation HITL est en attente, est refusé.

Chaque refus envoie au client un `SYSTEM_EVENT` de type `error` avec un message explicite.

## HITL : validation avant l'action

Le middleware HITL vérifie les tool calls issus du modèle avant le routage :

| Niveau annoncé par le tool | Décision |
| --- | --- |
| `none` ou `low` | Le tool peut poursuivre son exécution. |
| `high` ou `critical` | Une approbation utilisateur est demandée avant l'action. |

Le serveur permet aussi de bloquer explicitement un nom de tool :

```ts
server.blockTool('delete_account');
```

Pour les tools serveur :

- Déclarez toujours `risk`. Un tool serveur sans niveau de risque s'exécute sans approbation et le serveur l'indique au démarrage.
- Les arguments produits par le modèle sont vérifiés contre `parameters` (types, `required`, `enum`) avant d'appeler le handler.
- `apiKeys` réserve un tool à certaines applications. Il n'est alors ni proposé ni exécutable pour les autres clés :

```ts
server.tool('refund_order', {
  description: 'Rembourser une commande',
  risk: 'high',
  apiKeys: ['pk_backoffice'],
  parameters: { type: 'OBJECT', properties: { orderId: { type: 'STRING' } }, required: ['orderId'] },
}, refundOrder);
```

Une approbation n'est acceptée que de la session qui a reçu la demande. Le HITL protège l'utilisateur contre une action décidée par le modèle ; il ne remplace pas les contrôles métier côté serveur pour les actions sensibles (paiement, remboursement).

`OwlLayerServer` expose actuellement la méthode publique de blocage. Le niveau de risque est porté par la déclaration reçue dans la session : une action sensible doit être décrite comme telle au point où elle devient visible à l'agent.

## Comprendre les différents stockages

OwlLayer expose plusieurs familles de données. Elles ne répondent pas au même besoin :

| Besoin | Option `OwlLayerServer` | Comportement sans configuration | Implémentations exposées |
| --- | --- | --- | --- |
| Session et historique AITP | `sessionStore` | Session active conservée dans le runtime seulement. | `MemoryStore`, `MongoStore` |
| Mémoire agent structurée | `agentMemory` | Provider `memory`. | `memory`, `sqlite`, `mongo` |
| Métadonnées des API keys | `apiKeyStore` | `MemoryApiKeyStore`. | Memory, SQLite, Mongo |
| Prompts associés aux clés | `agentStore` | `MemoryAgentStore`. | Memory, SQLite, Mongo |

### Persister la mémoire agent en SQLite

```ts
const server = new OwlLayerServer({
  llm,
  agentMemory: {
    provider: 'sqlite',
    sqlitePath: './data/owllayer-memory.db',
    journalMode: 'WAL',
  },
});
```

Le `MemoryManager` initialise ce provider lors du démarrage, et les agents de session enregistrent leurs snapshots avant la destruction de leur session.

### Persister l'historique de session avec MongoDB

`MongoStore` nécessite une connexion explicite avant d'être remis au serveur :

```ts
import { OwlLayerServer, MongoStore } from '@owllayer/server';

const sessionStore = new MongoStore({
  uri: process.env.MONGODB_URI!,
  database: 'owllayer',
  collection: 'sessions',
});

await sessionStore.connect();

const server = new OwlLayerServer({
  llm,
  sessionStore,
});
```

## Surveillance et interface admin

Lorsque `admin` est configuré, `OwlLayerServer` installe l'API d'administration. L'option `ui.enabled` active l'interface embarquée, mais celle-ci nécessite l'authentification admin :

```ts
const server = new OwlLayerServer({
  llm,
  admin: {
    username: process.env.OWLLAYER_ADMIN_USER!,
    password: process.env.OWLLAYER_ADMIN_PASSWORD!,
  },
  ui: { enabled: true, path: '/owllayer-ui' },
});
```

Le mot de passe admin doit contenir au moins 12 caractères et ne pas être une valeur connue. Avec `NODE_ENV=production`, un mot de passe faible empêche le serveur de démarrer ; sinon, un avertissement est affiché.
